Talker–Thinker 双脑实时交互架构

小模型 MiniCPM-o 4.5(全双工 Talker)做实时听·看·说;大模型 Qwen3.5-35B-A3B(异步 Thinker)在旁持续思考、随时插话或叫停。支持双向打断:人能打断 AI,AI 也能打断人。

最新方案快照 · C 模式(异步旁路)+ 双向打断 · 基于已跑通的 MiniCPM-o demo 代码实测

TL;DR — Talker 实时驱动对话;Thinker(35B/3B 激活,SGLang 上跑)异步监看,输出 NOOP / INJECT / CUT 三类指令。 新增编排层负责 epoch 围栏(同时作废过期答案与过期 CUT)和 floor arbiter(谁持麦)。 人打断 AI = 原生(force_listen);AI 打断人(CUT)= 需小改小模型(break + 注入)。 Thinker 取消 = SGLang 实时 abort。

1 · 角色分工

Talker · 小

MiniCPM-o 4.5

全双工,~1s 微轮次(chunk_ms≈1000)。端到端 audio→audio,听/看/说一体,自带用户打断。跑原生 PyTorch duplex worker(已在 2×H100 上跑通)。

Thinker · 大

Qwen3.5-35B-A3B

MoE,35B 总参 / 仅 3B 激活 → 便宜到可以高频跑。跑在 SGLang(轮次制、高吞吐、支持实时 abort)。纯文本进出。

Orchestrator · 新

编排层

贴在网关上。维护滚动上下文、epoch 围栏、floor arbiter;把 Talker 事件转给 Thinker,把 Thinker 指令落回 Talker。不进模型权重,是外挂调度。

因为换了 35B-A3B,方案简化了一层:原计划的"便宜监工 + 贵大脑"两级 Thinker,在 3B 激活下基本没必要—— 直接让 35B-A3B 既当监工又当大脑、高频重跑即可。复杂度下降。

2 · 整体架构

数据流: 浏览器 ↔ Talker 走 WebRTC 音视频;Talker → 编排层送"自己的草稿文本 + 打断事件";编排层 → Thinker 送滚动上下文;Thinker → 编排层回 NOOP/INJECT/CUT 指令;编排层 → Talker 落成 force_listen / force_speak / 文本注入。红色虚线 = AI 主动打断(CUT)。

3 · 双向打断(本方案的核心)

方向触发落到 demo 代码代价
人 → AI
(用户插话)		 客户端 VAD 检测到说话 → 消息带 force_listen=true 模型下一步被强制 <|listen|>;正在说则先注入 <|turn_eos|> 收尾 + 重置 TTS ✅ 完全原生
不碰模型
AI → 人
(CUT 叫停)		 Thinker 输出流里出现 CUT{reason, redirect} break_event.set() 在 chunk 边界硬停 → 注入 [CUT] redirect 文本 → force_speak 念出来 ⚠️ 需小改小模型
无原生 force_speak
"立刻打断"能做多快? 服务端 _op_lock 串行,所以打断不是逐 token 瞬时,而是落在下一个 chunk 边界(几百 ms ~ 1s)。break_event 能中途叫停当前生成。对人耳而言"几百毫秒内闭嘴/开口"已经是自然的打断体感。

CUT 的两条实现路线

路线 1 · break + turn_based 插话 推荐起步路线 2 · 加 duplex_force_speak(text)
做法 CUT → break_event 停 duplex → 瞬时用 turn_based 把 redirect 念出(turn_based 有现成"文本→TTS"通道)→ 切回 duplex 在 DuplexCapability 加方法,直接注入合成 TTS embedding(绕过 LLM)→ token2wav
改模型几乎不改,复用现成路径要改模型代码,风险更高
体验切模式有小接缝duplex 内插话更顺滑

关于 #3:用 System Prompt 让它"看到 CUT 就打断"

诚实判断:能做"软触发",但不能当唯一硬保证。
把 [CUT] redirect 当文本注入 Talker 输入,并用 system prompt 约定"看到 [CUT] 立即停止聆听、开口说后面的内容"—— 这是行为塑造,但"被指令打断"很可能不在 duplex 模型训练分布里,纯靠 prompt 不稳。
稳的组合: break_event 硬停(代码保证"闭嘴")+ 注入文本 + system prompt 引导"自然地说出 redirect"。硬停归代码,自然度归 prompt。
👉 demo 正在运行,这条可以直接实测——写个小 WebSocket 客户端注入 [CUT] 看模型反应即可验证可靠性,再决定是否上路线 2。

4 · epoch 围栏:一套机制守住两个方向

Thinker 是在"几秒前的上下文"上推理的。无论它给的是答案还是 CUT,送达时世界可能已经变了(用户已自我纠正 / 已打断)。所以每条指令都带它计算时的 epoch,发出前校验。

事件动作
用户打断 / 出现新的实质输入state.epoch += 1 → SGLang abort 在飞的 Thinker 请求
Thinker 回 INJECT / CUT,但 directive.epoch ≠ state.epoch丢弃,绝不发声 / 绝不打断

口诀: abort 管"少算"(省 3B 的卡),epoch 管"不说 / 不乱打断"。两道闸,任意一道生效都安全。

5 · 两个关键流程

A. 用户打断 AI(原生)

  1. 用户开口,客户端 VAD 命中
  2. 下条消息带 force_listen=true
  3. Talker flush 当前 TTS,转 <|listen|>
  4. 编排层 epoch++ → abort Thinker
  5. 以用户新输入重启;过期答案被 epoch 丢弃

B. AI 主动叫停(CUT)

  1. Thinker 监看,判定方向跑偏
  2. 输出 CUT{redirect},带当前 epoch
  3. 编排层校验 epoch 仍有效 → break_event 硬停 Talker
  4. 注入 [CUT] redirect + force_speak
  5. Talker 用同一音色立刻说出 redirect;用户顶回来则让位(人优先)

7 · 落地路线 & 待定

分步走

  1. 编排层骨架:订阅 Talker 草稿 + 打断事件,接 SGLang(35B-A3B)
  2. 级联跑通:草稿→Thinker→INJECT 念回(先不打断)
  3. 加 epoch 围栏 + SGLang abort(守过期)
  4. CUT 路线1:break + turn_based 插话
  5. 实测 system-prompt 软触发,必要时上路线2

仍待拍板 / 验证

  • system-prompt 软触发可靠性 — 需 demo 实测
  • 人 vs AI 打断优先 — 默认人赢、CUT 让位
  • Thinker 取词 — 草稿桥接为主,是否加 Whisper 旁路拿用户原话?
  • Thinker 重跑频率 — 每轮 / 定时 / 事件触发(影响成本)
